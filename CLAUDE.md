## Status (as of 2026-09-25) — LIVE, deployed on this Windows server
- **Web**: https://newipo.finwave.co — Next.js **static export** (`apps/web/out`) served by IIS. Deploy = `cd apps/web && npm run build` (instant, no pool involved).
- **API**: https://newipoapi.finwave.co/api — NestJS via **iisnode** from `apps/api/dist`. Deploy needs the **app-pool handshake** (see below).
- **IIS app pools — the names are NOT what you expect.** `Investoyard` serves the **STATIC SITE**; `InvestoyardAPI` serves the API. Read that twice before changing a setting: the pool called "Investoyard" is the one that has nothing to do with `apps/api`. `appcmd` needs an **ELEVATED** shell (`list` returns Access Denied otherwise), and `applicationHost.config` is unreadable without it too — the System event log is the way to see pool behaviour from a normal shell.
  - **Both pools ran with IIS's default 20-minute IDLE TIMEOUT until 2026-09-24, and it caused two separate faults.** On the static pool it produced the operator's **522s**: after an idle shutdown the next visitor paid a cold start measured at **10.6 s** (4–129 ms once warm), and a low-traffic site makes most visitors that first request. On the API pool it was worse than slow — **the subscription poller lives inside that Node process, and IIS idle timeout counts REQUESTS, not activity**, so a `setInterval` does not keep the worker alive. `InvestoyardAPI` idled at 07:42 on 23-09 and stayed dead through the 10:00 window opening; nothing was polled until a visitor happened to wake it. **A background job cannot live in a pool IIS is allowed to shut down.**
  - **Both now run `idleTimeout:00:00:00` + `startMode:AlwaysRunning`**, with the rolling 29-hour recycle replaced by a fixed **04:00** schedule (`recycling.periodicRestart.time:00:00:00` + a `schedule.[value='04:00:00']` entry) — six hours clear of the poll window, and on the static pool it stops a random-hour recycle handing someone that 10.6 s again. `logEventOnProcessModel:"IdleTimeout"` is on, so a regression shows up in the System log as a WAS **5186**.
- **DB/Redis**: portable Postgres :5433 + Redis :6379 — **NO Docker**. After any reboot: `scripts\db.ps1 start` + `scripts\redis.ps1 start` (or `scripts\start-services.bat`). A downed DB looks like a CORS/500.
  - **Postgres RUNS AS A WINDOWS SERVICE** — `investoyard-postgres`, LocalSystem, auto-start, restart-on-failure 5s/10s/30s (registered 2026-09-23). It has no console, so the Ctrl+C that killed it three times that day cannot reach it, and it comes back after a reboot on its own. `db.ps1` is service-aware (`start|stop|status|register|unregister`): it drives the service when one exists and falls back to `pg_ctl` when it doesn't, so it behaves the same either side of registration. **`register`/`unregister`/`Restart-Service` need an ELEVATED shell** (SeCreateServicePrivilege); `register` checks that BEFORE stopping anything, so a refusal costs nothing. LocalSystem is safe because `pg_ctl` spawns postgres with a RESTRICTED token — Postgres aborts if it holds administrator rights, which is also why this goes through `pg_ctl register` and not `sc create`.
  - **Under the service, `pg_ctl status` LIES — use `pg_isready`.** The postmaster runs as LocalSystem and a standard user cannot open a handle to it, so `pg_ctl status` reports *"no server running"* for a database answering every query. `db.ps1` briefly announced ZOMBIE over a healthy service because of it. Liveness is now defined as **accepting connections** everywhere it matters, and that check is the FIRST guard in `Clear-PgZombie` — a zombie is by definition a server that does not accept connections, so a healthy service can never match whatever `pg_ctl` thinks. (`pg_isready` reports *accepting connections* even when auth fails — it connects as the OS user, so `role "finwave" does not exist` in the log is that probe, and is exactly the answer a liveness check wants.)
  - **Server logs moved to `.pgdata\log\postgresql-YYYY-MM-DD.log`** via `logging_collector = on` (2026-09-23; daily / 50 MB rotation, settings appended at the end of `postgresql.conf`, backup `postgresql.conf.bak-20260923`). **`.pgdata\log.txt` is FROZEN** at the last console-started server's shutdown — do not read it for anything recent. A service sends stderr to the Windows event log, where every line renders as *"The description for Event ID '0' in Source 'PostgreSQL' cannot be found"* because `pgevent.dll` is not registered; the collector sidesteps that and survives re-registration. `log_min_messages` is `warning`, which still captures crashes — **LOG outranks WARNING** in the server-log ordering.
  - **A crashed Postgres leaves a ZOMBIE**, and `db.ps1 start` now clears it automatically (2026-09-23). Symptom set: `pg_ctl status` says **"no server running"**, yet a `postgres` process is alive, **5433 is still LISTENING**, and `start` warns *"another server might be running"* then fails with *"could not open log file … Permission denied"* — the orphan holds both the socket and the log. `Clear-PgZombie` acts only on that exact three-way combination (no postmaster **and** orphan processes **and** the port held); anything looser would be killing a healthy server, and it removes `postmaster.pid` only once both are provably gone. WAL replay on the next start is the normal, non-destructive recovery; nothing committed is lost.
  - **Check Postgres by CONNECTING, never by probing :5433.** An orphaned backend keeps the listening socket, so an open port is exactly what a crashed server looks like — `start-services.bat` used to test the port and reported **UP** for a database refusing every query, while also telling the operator that the zombie's warnings meant *"Postgres was ALREADY running - that is fine"*. Both are gone. The check is now `pg_isready -h 127.0.0.1 -p 5433` (expect *accepting connections*) and `redis-cli -p 6379 ping` (expect *PONG*), and the API is the final word: `curl -H 'Host: newipoapi.finwave.co' http://127.0.0.1/api/health` must be **200**, not 503.
  - **Never `npm run build` the web while the API is down** — the static export is generated from the LOCAL live API (`API_INTERNAL_URL=http://localhost:3000/api`, via the Host-header forwarder). Against a dead API it bakes an empty catalog AND collapses every dynamic route to the `no-ipos` placeholder, wiping ~1,000 real IPO pages. The build log naming 1,000 `/ipos/[symbol]` paths is the proof it had real data.
  - **A build that ran while the DB was dying POISONS `.next/cache`, and plain rebuilds replay it.** `safeGet()` uses a cacheable `fetch` (required by `output: export`), so a failed response is cached like any other and **two clean rebuilds against a healthy API reproduced the damage exactly** (2026-09-23). The cure is to clear the fetch cache before rebuilding — the comment on `safeGet` says so, and it is easy to read past. **Clear `apps\web\.next\cache\fetch-cache` only** (~3 MB), not all of `.next\cache`: the sibling `webpack` folder is ~180 MB of compilation cache and nuking it costs minutes for nothing. **Any rebuild meant to pick up changed DB data needs this** — not just one after an outage.
  - **The failure is PARTIAL and silent, which is what makes it dangerous.** The build does not fail: `safeGet` swallows the error and returns its fallback, so the log still prints ~1,000 routes and looks perfect while individual pages lose whole sections. On 2026-09-23 four IPOs that were OPEN shipped detail pages with no Live Subscription section at all. **Route count is not proof of a good build** — spot-check a page's content: `grep -c timesSubscribed apps/web/out/ipos/<slug>/index.html` should be non-zero for anything currently subscribed.
- **Mobile**: Expo **SDK 54** (Play-Store Expo Go works). Dev: `cd apps\mobile; $env:REACT_NATIVE_PACKAGER_HOSTNAME='103.107.27.38'; $env:EXPO_OFFLINE='1'; npx expo start --clear`.

### API deploy handshake (CRITICAL)
iisnode locks `dist` + the Prisma engine DLL while the pool runs. **User** stops the pool → then:
`npx prisma generate` (only if schema changed) → `npx tsc -p tsconfig.json --outDir dist` → **user** starts the pool.
- `npx prisma db push --skip-generate` is SAFE while the pool runs; `prisma generate` is NOT.
- New-Prisma-model code shows "property does not exist on PrismaService" typecheck errors until the handshake — expected, not a bug.
- **NEVER run root `npm run build` (turbo) while the pool runs** — nest's clean step guts `dist` and causes a delayed outage. Build workspaces individually.
- Seed is CLEAN-SLATE — never run against prod. Use `npm run ensure-roles` for additive role changes.
- **ALWAYS boot-test before handing the build back**: `PORT=3999 node dist/main.js` and look for "Nest application successfully started". `tsc` passing proves NOTHING about dependency injection — a controller injecting a service whose module wasn't imported fails at BOOT and takes down **every** endpoint with a 500, not just the new route. That happened (`TemplateTestController` → `WhatsappService`, `WhatsappModule` not imported; it is not `@Global`).
- **`web.config` has `loggingEnabled="false"` — there are no iisnode log files.** To see why the API is failing, run the compiled app directly; the Nest error prints in one shot.
- To prove a fix **while the pool is still up**, compile to a scratch dir INSIDE the repo (`--outDir dist-check`, so `node_modules` still resolves), boot-test that, then delete it. `dist` is locked while iisnode runs.

Final tie-break is **symbol** — four issues sharing a stage AND a close date is ordinary, and returning 0 left the order to whatever the API sent, so the same four rendered Elevate-first in one build and Swastika-first in the next. Deliberately NOT subscription: those numbers change on every poll, so a card would move under the reader's cursor.

Every web API client (`consumer-api.ts`, `tenants-admin.ts`) reads the body as text and treats an empty 200 as `null`. This broke `/partner/apply` for every first-time visitor.
- **`runUnscoped` is not enough on its own for cross-tenant reads on a pooled connection.** `PrismaService`'s tenant extension wraps scoped queries in `$transaction([set_config('app.current_tenant_id', <tid>, true), query])` — `is_local=true` means the GUC resets at transaction end, which works in isolation. ''}, true)`, findFirst])` — deterministically resets (or narrows to `scope`) before the read, whatever state the connection was in. See `partner.service.ts printDetail` for the reference.

## Subscription poller — cadence + tuning
- **Live-tunable via `admin → Integrations → 'Live subscription poller — cadence & window'`**. Provider key `subscription` with fields: `normalSec` (default 60), `fastSec` (default 5), `fastWindowMin` (default 90), `fromMin` (default 600 = 10:00), `toMin` (default 1080 = 18:00). Poller reads `providers.effective('subscription')` on each tick with the 60s config cache TTL, so overrides take effect within a minute — **no pool restart** needed for cadence tweaks. Bad values (non-numeric, ≤0) fall back to defaults per-field so a typo can't stall the loop.
- **Window: 10:00–18:00 IST**. `OPEN_TO_MIN` is `18 * 60` — 1-hour grace past the 17:00 SEBI bidding cutoff so NSE catwise and BSE demand-schedule can serve consolidated / finalized numbers for another 30-60 min on closing day. Was 17:00 sharp until 2026-09-21 when NSE's final subscription never got written.
- **Fast mode**: last 90 min before 17:00 (i.e., from 15:30 IST) AND through the 17:00-18:00 grace hour uses `FAST_MS` (5s default) instead of `NORMAL_MS` (60s default). `BIDDING_CLOSE_MIN = 17 * 60` is the fixed regulatory anchor for the fast-window trigger; `OPEN_TO_MIN` (poller cutoff) is separate and tunable.
- **BSE per-category bids are FUDGED** (per operator's original C# workflow) — BSE ships `totalapplication` as a scalar for the whole issue. Back-solve for hni / hni2 / shareholder / **employee** from NSE avg shares-per-bid; retail absorbs the remainder. Employee was excluded from this loop until 2026-09-21 (NSE closing day) — Employee BSE bids were silently folded into Retail's residual, understating Employee applications by 12k+ and inflating Retail by the same.
- **60s config cache TTL** is the whole reason live tuning works without a restart. The `subscription` provider config's settings JSON drives cadence directly.
- **An EMPTY read is missing data, not zero demand** (`keepKnownFigures`, 2026-09-23). The write is DESTRUCTIVE — `deleteMany` + `createMany` — so whatever `computeSubs` returns becomes the entire truth for the issue, and `computeSubs` emits `timesSubscribed: 0` with no share columns for a category the exchange said nothing about (it only sets `nseShares` when `r.ns > 0`). One empty tick therefore erased a real figure permanently: ELEVATE's QIB held 32,25,142 shares — the number every other site showed and the number our own built page still carried — and was replaced by 0 for the rest of the day. **That is what "the count shows then goes to zero on refresh" means**: the page renders the baked figure, then the 60s refresh pulls the zeroed row. ADROITIND lost `1,06,116 → 1,03,008` the same way. Subscription inside the window is CUMULATIVE, so a category cannot go from 3.2 million shares to nothing. The guard carries a category forward when a tick reads **completely** empty (no shares either side AND times 0) while a real figure is stored, and re-adds a category dropped from the response entirely; both log a warning. **A SMALLER number still overwrites a bigger one** — exchanges do revise down, and clamping to the day's maximum would freeze a correction we could only undo by hand.
- **The poller writes `extra` with a jsonb MERGE, and must never go back to a read-modify-write** (2026-09-25). `refreshIpo` used to write `extra: { ...ex, subLog, subLogHour }`, where `ex` was read at the TOP of the method — **two network round trips earlier**, to NSE and to BSE. Everything written to `extra` inside that gap was silently reverted by the poller's stale copy, on every LIVE issue, once a minute — and **once every FIVE SECONDS after 15:30**, when fast mode starts. It is now `SET extra = COALESCE(extra,'{}'::jsonb) || $1::jsonb`, evaluated inside Postgres against the CURRENT row, so the window does not exist and the poller cannot touch a key it did not write.
  - **This is `SERVER_OWNED_EXTRA` enforced from the other side**: that whitelist stops the form deleting the poller's four keys; this stops the poller deleting everything else. Both faults are the same shape — two writers, one unschema'd JSON column, last write wins the whole thing.
  - **The operator's own saves were at risk, which is the part that matters.** `ipo.service.update()` is also a read-modify-write of this column, so a Book Size corrected mid-issue could vanish with nothing to show it ever landed — on a live IPO, which is exactly when an operator edits one.
  - **How it surfaced, and the lesson**: a provenance backfill reported *8 rows stamped across 2 IPOs* and only ORIENTCABL's four survived; ACEVECTOR's were gone before the next read. **A script that reports success has only proved it issued the write** — re-read after writing to a live record, or the loss is invisible. The merge was proved on a closed record before deploy: 57 keys in, 59 out, **none lost**, `shareResv` untouched.
  - `Ipo` carries **no RLS policy** (`setup-rls.sql` scopes User · InvestorProfile · Consent · Application · WatchlistItem · DeviceToken), so a raw statement on that table needs no tenant GUC. A raw write to any of those six does — see the `runUnscoped` note under Conventions.
  - **ONLY `extra` moved to raw SQL. `subscriptionAsOf` stays on the Prisma path in BOTH branches**, and that is not fussiness: the column is `timestamp without time zone` and the two writers disagree about what it means. Prisma stores **IST wall-clock** (`14:08`), a raw parameter stores **true UTC** (`08:37`). Writing it in the raw statement split the column between the two branches — caught in verification on 2026-09-25 with ACEVECTOR at `08:37:28` beside ORIENTCABL at `14:08:20`, seconds apart in real time. **Moving one column to raw SQL must not silently redefine another.** (The rows self-healed within a minute, because the next poll rewrites the timestamp either way.)
  - **Proved in production, not just in theory**: a sentinel key merged onto ACEVECTOR's `extra` while it was live survived the next poller write 50s later, 60 keys → 61, `shareResv.qib.source` still `derived`. Before the fix that key is exactly what vanished.
- ~~**`subscriptionAsOf` reads 5½ HOURS FAST**~~ **FIXED 2026-09-25 — and it was the whole database, not one column.** The operator reported *"Updated 25-Sep-2026 8:19 PM"* at 2:49 PM. The chain: the column was **naive** (`timestamp without time zone`), the connection runs at `Asia/Calcutta` so the driver's `…T14:51+05:30` lost its offset and Postgres stored the **IST wall-clock**; Prisma read that back **as if UTC**; `toDetail()` stamped it `Z` with `.toISOString()`; and `fmtDateTime()` rendered it with `getHours()` — the viewer's zone. **Stamped in IST, labelled UTC, rendered back into IST**, so +5:30 landed exactly once.
  - **All 76 timestamp columns were naive** and **eight** UI sites render one in local time (the subscription card plus allotment import, audit-live, GMP log, message-template log, partner applications). Fixing only the reported field would have left a mixed database — the same trap as the poller's two branches.
  - **`ALTER … TYPE timestamptz USING col AT TIME ZONE 'Asia/Kolkata'`** reads each stored value *as IST*, which is what it actually is, so **the type change corrects every row as it converts** — no separate backfill and no half-converted window. `scripts/timestamps-to-timestamptz.js` (dry-run by default) does all of them in ONE transaction.
  - **No code deploy was needed.** The running app, whose Prisma client was generated against `timestamp`, wrote correct instants into the converted column immediately — verified against the live poller before touching the other 75. The `@db.Timestamptz(3)` annotations exist only so a future `prisma db push` cannot revert the columns.
  - **THE TRAP, and it was live for minutes: four DATE-ONLY columns.** `Ipo.openDate` · `closeDate` · `allotmentDate` · `listingDate` hold midnight. Converted, `2026-09-25 00:00` became `00:00+05:30` = **18:30Z on the 24th**, and `day()` (`toISOString().slice(0,10)`) read **one day early** — which on a close date flips a LIVE issue to closed. Fixed by pinning them to UTC midnight of their IST date (`((col AT TIME ZONE 'Asia/Kolkata')::date)::timestamp AT TIME ZONE 'UTC'`, written that way so a re-run is a no-op). **A date living in a timestamp column does not survive a timezone conversion — find those columns FIRST** (every non-null value at IST midnight is the test) and treat them separately.
  - **Precision is part of the type.** A plain `TYPE timestamptz` produced precision **6** while Prisma wants **(3)**, so `prisma migrate diff` still showed 76 alterations. Re-pinned at `timestamptz(3)`; the diff is now *"This is an empty migration"*, which is the only proof that schema and database agree.
  - **Verified against a snapshot that predates the change**: 60 of 60 IPOs' open dates match the static export built before the conversion, and the card now reads 3:02 PM at 3:03 PM.
- **Manual refresh returning `0 of 3 open updated` is NORMAL**: `refreshIpo` returns `true` only when numbers CHANGE, `false` when they're identical to the last snapshot (writes-on-change gate). "Updated" ≠ "polled" — all 3 IPOs are still being queried.

## ASBA print — flatten guarantee for WhatsApp forwarding
- **`fillAsbaAcroForm()` in `apps/api/.../asba-acroform.ts`** guarantees a **fully-flat PDF** on the `flatten=true` path. When per-field appearance streams don't all build (ARDEE-style blanks missing `/DR`/`/DA`), fast `form.flatten()` bails — the code then **burn-ins** each field's value at its widget `/Rect` using the embedded Helvetica AND removes every widget annotation from every page's `/Annots` array (both live widgets AND dangling `PDFRef`s from the earlier bad-widget cleanup). Then deletes the AcroForm shell.
- **Why widgets matter**: `pdf-lib`'s `form.removeField()` only unlinks a widget's annotation from a page when the widget's `/P` (page ref) is set. Many SEBI templates skip `/P`, so removeField leaves orphan widgets. Viewers still render highlighted empty form-field boxes over the burned-in text — the PDF LOOKS half-filled. The belt-and-braces sweep of every page's `/Annots` catches both live widget dicts AND dangling refs. ELEVATE_TEST.pdf: 38 orphan widgets → 12 (dangling) → **0** ✓.
- **Why this exists**: WhatsApp's in-app viewer (Android + iOS) **ignores `/NeedAppearances`**. Adobe Reader / Chrome / iOS Files honour it and regenerate appearances at open time; WhatsApp doesn't. Every partner-API PDF is forwarded through WhatsApp by the operator's brokers, so `/NeedAppearances` fallback = customer receives a blank form. Guaranteed flat = works everywhere.
