One platform, three go-to-market models

How Investoyard serves direct customers (B2C), multi-branch partners (B2B2C), and white-label clients — from a single codebase, a single database, and a single deployment.

The core principle. We don't build three apps. We build one multi-tenant platform, and the three models are simply configurations of a single Tenant. They differ on only two independent axes — who sees the data (identity) and which brand/domain serves it (presentation). The Partner model is a data-scoping concern; White-label is a branding concern. Both ride the same backbone.

2The Tenant backbone (a self-referential tree)

Every business record carries a tenantId. That one column powers isolation, roll-up reporting, and branding. White-label is just a flag + custom domain on a partner node.

Platform = operator (sees all). B2C customers live in the Investoyard Direct channel · partner admins see their subtree · branches see only themselves.

3How a request finds its tenant

White-label resolves by domain; partner/branch resolves by authenticated user — both feed one tenant context.

Decided approach — server-side (SSR), by domain. On every page load — including the public landing page where no one is logged in — the server reads the request's Host header and resolves the tenant from the domain: our domains → the platform (Investoyard) brand; a partner's registered custom domain → that partner's tenant. The user's login then narrows the data scope after sign-in. One codebase; the brand is decided per request, never baked into the files — matching Investoyard's current host-based logic.

4Data isolation & scoping

Shared DB, two enforcement layers

One PostgreSQL, a tenantId on every business table. 1) ORM middleware auto-injects the tenant filter on every query — no manual filters, no leaks. 2) Postgres Row-Level Security as defense-in-depth: even a buggy query physically cannot read another tenant's rows.

6Data model — what changes

New: Tenant (tree via parentId, type, branding, flags, railConfig) · Role (tenant-aware permissions) · Membership (User → Tenant → Role).
Add tenantId to: User, InvestorProfile, Consent, Application, Watchlist, DeviceToken, MemberCredential.
Stays global (shared reference data): the IPO catalog — Ipo, subscription, GMP, documents.
New consent type: data_sharing_partner for B2B2C acquisition (DPDP).
Tenant types: platform (operator root, no customers) · direct (Investoyard Direct — B2C) · partner · branch. Every customer belongs to a channel (direct / partner / branch); the platform root is operator-only.

Applicant identity & IPO application categories

• PAN is unique per tenant — one investor profile per PAN within a tenant (@@unique([tenantId, panHash])); the same PAN may exist under another tenant. PAN stays vaulted; a keyed hash is used only for dedup.  • Three application categories — Individual, Shareholder, Employee. One PAN may apply once in each per IPO (up to 3), never twice in the same category (@@unique([ipoId, investorProfileId, applicantCategory])); market-wide same-PAN dedup remains the registrar's job.  • Admin enables the allowed categories per IPO (Ipo.allowedApplicantCategories); a tenant may further narrow them via the settings cascade.

8Security, audit & regulatory compliance

Regulatory (as applicable to our role / empaneling banker)

• SEBI Cyber Security & Cyber Resilience Framework (CSCRF) — align as required by the empaneling merchant-banker.  • CERT-In directions — 6-hour incident reporting, ≥180-day logs held in India, NTP time-sync.  • DPDP Act 2023 — itemised consent, data-sharing consent to partner, breach notification.  • ISO/IEC 27001 ISMS (target).  • Data residency in India.

Security controls

• Periodic VAPT by an independent, CERT-In empanelled third-party vendor — black-box (outsider, no access), grey-box, and white-box (full source + architecture) testing; before go-live, ≥ annually and after major releases; scope explicitly includes multi-tenant isolation and the public APIs.  • Secure SDLC — SAST, DAST, dependency & secret scanning in CI.  • WAF + DDoS, rate-limiting.  • Encryption — TLS 1.2+/1.3 in transit, AES-256 at rest, PII in a KMS-backed vault.  • MFA for all staff, least-privilege RBAC.  • Backups + DR (RPO/RTO), incident-response plan.

API & access security — no direct / unauthorised use

Every endpoint requires a valid, short-lived, signed token — no anonymous or direct API access. The backend sits behind an API gateway + WAF on a private network (not internet-reachable directly); with a CORS allow-list, CSRF protection, HMAC-signed sensitive calls, mTLS for rail / server-to-server, rate-limiting + bot/DDoS protection, replay / idempotency guards, and strict request-schema validation. Even a valid token is confined to its own tenant by RLS — it can never reach another tenant's data.

Data-layer musts: isolation enforced at the ORM + Postgres RLS layer (never per-endpoint) · per-tenant secrets in a vault · custom domains verified (TXT) before activation · tenant-scoped audit log · CI test "tenant A can never read tenant B" · self-PAN rule universal (each applicant applies with their own PAN / demat / UPI).

Chosen: Node (NestJS). The database is PostgreSQL — the best-supported, lowest-friction pairing for Node / Prisma, with best-in-class JSON (JSONB) for our config cascade, mature Row-Level Security, and no licensing cost as we scale. SQL Server is also supported (Prisma has a SQL Server driver) — choose it only to reuse existing SQL Server DBAs / licences. The multi-tenant design (RLS + ORM query filters) is the same on either DB; web + mobile are unchanged.

10Performance & scale

IPO traffic is spiky but predictable — it surges in the last day / last hour before a popular IPO closes, plus constant refreshing of live subscription & GMP. Because the calendar is known, we design for the spike and pre-scale for it. Two rules carry it — cache the reads, queue the writes — using only in-house (free) infrastructure.

Reads → in-house caching

Most traffic is browsing IPO / GMP / subscription. Served from cache, not rebuilt per request: Next.js ISR (regenerate a page every few seconds) · Redis for the catalog, live snapshots & tenant config · reverse-proxy cache (IIS / Nginx) · gzip / Brotli compression + cache headers. Thousands of identical requests collapse to one.

Writes (Apply) → queue & meter

The apply-rush never hits the exchange synchronously — accept → BullMQ queue → workers submit to NSE/BSE at a controlled rate; the user instantly sees "submitted · processing", status arrives via the exchange callback. 50,000 last-hour applications just fill a queue that drains steadily. Idempotency keys make retries safe.

Reads are absorbed by in-house cache (no rebuild); the apply-rush is queued and sent to the exchange at a steady, safe rate.

Also: live subscription / GMP fetched once every few seconds into a Redis snapshot all users read (N requests → 1 upstream fetch; mobile via FCM push, not polling) · Postgres read replicas + PgBouncer pooling · stateless API + workers auto-scale horizontally (on CPU + queue depth) · rate-limiting stops bots / scrapers · pre-scale on the IPO calendar + load-test (k6 / JMeter) before go-live · monitoring + graceful degradation (circuit breakers; a flag to slow live-refresh under extreme load).
