## Status (as of 2026-09-30) — LIVE, deployed on this Windows server
- **Web**: https://newipo.finwave.co — Next.js **static export** (`apps/web/out`) served by IIS. Deploy = `cd apps/web && npm run build` (no pool involved).
  - **THE DEPLOY IS NOT INVISIBLE TO VISITORS, and "instant" was the wrong word** (diagnosed 2026-10-09 after hitting it twice in one afternoon). A build rewrites all ~2,596 pages plus every hashed asset in `out/`; a request landing in that window stalls, **Cloudflare records a 522 — and then SERVES THAT CACHED 522 for that URL after the origin has fully recovered.** Proof: the origin answered `/subscription/v2/` in **140 ms** while Cloudflare returned 522 for `?symbol=SAIURJA`, and the identical URL with a cache-buster (`&cb=1`) loaded instantly. **A 522 that survives a healthy origin is a CACHED 522, not a cold start** — append a query parameter to tell the two apart. This is a better explanation of the operator's historical intermittent 522s than the idle timeout alone, and it is unresolved: the idle-timeout fix below does not touch it.
- **API**: https://newipoapi.finwave.co/api — NestJS via **iisnode** from `apps/api/dist`. Deploy needs the **app-pool handshake** (see below).
- **IIS app pools — the names are NOT what you expect.** `Investoyard` serves the **STATIC SITE**; `InvestoyardAPI` serves the API. Read that twice before changing a setting: the pool called "Investoyard" is the one that has nothing to do with `apps/api`. `appcmd` needs an **ELEVATED** shell (`list` returns Access Denied otherwise), and `applicationHost.config` is unreadable without it too — the System event log is the way to see pool behaviour from a normal shell.
  - **Both pools ran with IIS's default 20-minute IDLE TIMEOUT until 2026-09-24, and it caused two separate faults.** On the static pool it produced the operator's **522s**: after an idle shutdown the next visitor paid a cold start measured at **10.6 s** (4–129 ms once warm), and a low-traffic site makes most visitors that first request. On the API pool it was worse than slow — **the subscription poller lives inside that Node process, and IIS idle timeout counts REQUESTS, not activity**, so a `setInterval` does not keep the worker alive. `InvestoyardAPI` idled at 07:42 on 23-09 and stayed dead through the 10:00 window opening; nothing was polled until a visitor happened to wake it. **A background job cannot live in a pool IIS is allowed to shut down.**
  - **Both now run `idleTimeout:00:00:00` + `startMode:AlwaysRunning`**, with the rolling 29-hour recycle replaced by a fixed **04:00** schedule (`recycling.periodicRestart.time:00:00:00` + a `schedule.[value='04:00:00']` entry) — six hours clear of the poll window, and on the static pool it stops a random-hour recycle handing someone that 10.6 s again. `logEventOnProcessModel:"IdleTimeout"` is on, so a regression shows up in the System log as a WAS **5186**.
- **DB/Redis**: portable Postgres :5433 + Redis :6379 — **NO Docker**. After any reboot: `scripts\db.ps1 start` + `scripts\redis.ps1 start` (or `scripts\start-services.bat`). A downed DB looks like a CORS/500.
  - **Postgres RUNS AS A WINDOWS SERVICE** — `investoyard-postgres`, LocalSystem, auto-start, restart-on-failure 5s/10s/30s (registered 2026-09-23). It has no console, so the Ctrl+C that killed it three times that day cannot reach it, and it comes back after a reboot on its own. `db.ps1` is service-aware (`start|stop|status|register|unregister`): it drives the service when one exists and falls back to `pg_ctl` when it doesn't, so it behaves the same either side of registration. **`register`/`unregister`/`Restart-Service` need an ELEVATED shell** (SeCreateServicePrivilege); `register` checks that BEFORE stopping anything, so a refusal costs nothing. LocalSystem is safe because `pg_ctl` spawns postgres with a RESTRICTED token — Postgres aborts if it holds administrator rights, which is also why this goes through `pg_ctl register` and not `sc create`.
  - **Under the service, `pg_ctl status` LIES — use `pg_isready`.** The postmaster runs as LocalSystem and a standard user cannot open a handle to it, so `pg_ctl status` reports *"no server running"* for a database answering every query. `db.ps1` briefly announced ZOMBIE over a healthy service because of it. Liveness is now defined as **accepting connections** everywhere it matters, and that check is the FIRST guard in `Clear-PgZombie` — a zombie is by definition a server that does not accept connections, so a healthy service can never match whatever `pg_ctl` thinks. (`pg_isready` reports *accepting connections* even when auth fails — it connects as the OS user, so `role "finwave" does not exist` in the log is that probe, and is exactly the answer a liveness check wants.)
  - **Server logs moved to `.pgdata\log\postgresql-YYYY-MM-DD.log`** via `logging_collector = on` (2026-09-23; daily / 50 MB rotation, settings appended at the end of `postgresql.conf`, backup `postgresql.conf.bak-20260923`). **`.pgdata\log.txt` is FROZEN** at the last console-started server's shutdown — do not read it for anything recent. A service sends stderr to the Windows event log, where every line renders as *"The description for Event ID '0' in Source 'PostgreSQL' cannot be found"* because `pgevent.dll` is not registered; the collector sidesteps that and survives re-registration. `log_min_messages` is `warning`, which still captures crashes — **LOG outranks WARNING** in the server-log ordering.
  - **A crashed Postgres leaves a ZOMBIE**, and `db.ps1 start` now clears it automatically (2026-09-23). Symptom set: `pg_ctl status` says **"no server running"**, yet a `postgres` process is alive, **5433 is still LISTENING**, and `start` warns *"another server might be running"* then fails with *"could not open log file … Permission denied"* — the orphan holds both the socket and the log. `Clear-PgZombie` acts only on that exact three-way combination (no postmaster **and** orphan processes **and** the port held); anything looser would be killing a healthy server, and it removes `postmaster.pid` only once both are provably gone. WAL replay on the next start is the normal, non-destructive recovery; nothing committed is lost.
  - **Check Postgres by CONNECTING, never by probing :5433.** An orphaned backend keeps the listening socket, so an open port is exactly what a crashed server looks like — `start-services.bat` used to test the port and reported **UP** for a database refusing every query, while also telling the operator that the zombie's warnings meant *"Postgres was ALREADY running - that is fine"*. Both are gone. The check is now `pg_isready -h 127.0.0.1 -p 5433` (expect *accepting connections*) and `redis-cli -p 6379 ping` (expect *PONG*), and the API is the final word: `curl -H 'Host: newipoapi.finwave.co' http://127.0.0.1/api/health` must be **200**, not 503.
  - **Never `npm run build` the web while the API is down** — the static export is generated from the LOCAL live API (`API_INTERNAL_URL=http://localhost:3000/api`, via the Host-header forwarder). Against a dead API it bakes an empty catalog AND collapses every dynamic route to the `no-ipos` placeholder, wiping ~1,000 real IPO pages. The build log naming 1,000 `/ipos/[symbol]` paths is the proof it had real data.
  - **A build that ran while the DB was dying POISONS `.next/cache`, and plain rebuilds replay it.** `safeGet()` uses a cacheable `fetch` (required by `output: export`), so a failed response is cached like any other and **two clean rebuilds against a healthy API reproduced the damage exactly** (2026-09-23). The cure is to clear the fetch cache before rebuilding — the comment on `safeGet` says so, and it is easy to read past. **Clear `apps\web\.next\cache\fetch-cache` only** (~3 MB), not all of `.next\cache`: the sibling `webpack` folder is ~180 MB of compilation cache and nuking it costs minutes for nothing. **Any rebuild meant to pick up changed DB data needs this** — not just one after an outage.
  - **The failure is PARTIAL and silent, which is what makes it dangerous.** The build does not fail: `safeGet` swallows the error and returns its fallback, so the log still prints ~1,000 routes and looks perfect while individual pages lose whole sections. On 2026-09-23 four IPOs that were OPEN shipped detail pages with no Live Subscription section at all. **Route count is not proof of a good build** — spot-check a page's content: `grep -c timesSubscribed apps/web/out/ipos/<slug>/index.html` should be non-zero for anything currently subscribed.
- **Mobile**: Expo **SDK 54** (Play-Store Expo Go works). Dev: `cd apps\mobile; $env:REACT_NATIVE_PACKAGER_HOSTNAME='103.107.27.38'; $env:EXPO_OFFLINE='1'; npx expo start --clear`.

### API deploy handshake (CRITICAL)
iisnode locks `dist` + the Prisma engine DLL while the pool runs. **User** stops the pool → then:
`npx prisma generate` (only if schema changed) → `npx tsc -p tsconfig.json --outDir dist` → **user** starts the pool.
- `npx prisma db push --skip-generate` is SAFE while the pool runs; `prisma generate` is NOT.
- New-Prisma-model code shows "property does not exist on PrismaService" typecheck errors until the handshake — expected, not a bug.
- **NEVER run root `npm run build` (turbo) while the pool runs** — nest's clean step guts `dist` and causes a delayed outage. Build workspaces individually.
- **The PII VAULT KEY is the single point of total data loss. It lives at `C:\ProgramData\Investoyard\pii-vault.key`** (since 2026-09-28) — **outside** the build output, because it used to default to `process.cwd()/.pii-vault.key` and under iisnode that is `apps/api/dist`. One `rm -rf dist` deleted it and the app silently minted a replacement, came up healthy, and re-keyed the vault under everyone: the SMTP password, the Anthropic key and the exchange rail credentials all stopped resolving, which is why the subscription poller died with an authentication error.
  - **The key existed in FOUR places and only one of them mattered — check them all before declaring loss.** A first pass concluded 605 investor PAN tokens were gone. They were not: **`D:\Investoyard\.pii-vault.key` (Aug 29) is the original**, left behind by a run whose cwd was the repo root, and it decrypts **601 of 631** tokens and reproduces their stored `panHash` **397/397 on sample**. `apps/api/.pii-vault.key` (Jul 28) decrypts nothing. The minted `dist` key covers the ~26 written after the incident. Three profiles (ASH PATEL, ABHI PATEL, HIRAL SONI, all created in early August) open under no key at all and were **already broken before this** — unrelated. The lesson is the diagnosis, not the deletion: **`cwd` moves between deployments, so a cwd-relative secret scatters copies across every directory the app was ever started from.** Enumerate them and test each against real ciphertext before telling anyone data is lost.
  - **THREE distinct keys exist on this box, and only one decrypts anything.** Audited 2026-09-28 — do not re-derive this: **#1 `D:\Investoyard\.pii-vault.key` (Aug 29) is the ORIGINAL** and is what `C:\ProgramData\Investoyard\pii-vault.key` now holds · **#2 `apps\api\.pii-vault.key` (Jul 28) decrypts NOTHING** · **#3 `apps\api\dist\.pii-vault.key` (Sep 28)** was minted during the incident and covers only what was written after it. A key file is 64 bytes and they are indistinguishable by eye — **fingerprint them (`sha256` of the trimmed contents) rather than guessing from a filename or a date.**
  - **A backup named after a FILE is wrong the moment that file's contents change.** `pii-vault.key.backup-20260928-145551` was taken before the primary was swapped, so it promised a copy of `pii-vault.key` while holding key #3 — restoring it in an emergency would have re-broken exactly what the swap fixed. Deleted; its bytes survive as `archive-minted-sep28.key`, and the live backup is **`BACKUP-of-primary-original-aug29.key`**, verified identical to the primary. **Name a key backup after the KEY, never after the path it happened to sit at.**
  - **`find /` in Git Bash does NOT span Windows drives** — a search for stray key copies returned empty because `/` is the Git install root, not `D:`. It looked like proof that no other copy existed; there were five. Use PowerShell (`Get-ChildItem -Recurse`) with explicit roots for anything filesystem-wide on this box, and **never read an empty result from a search you have not confirmed can see the data.**
  - **`C:\ProgramData\Investoyard\` holds the primary, a correctly-named backup, and an archive of every key found** (`archive-original-aug29.key`, `archive-appsapi-jul28.key`, `archive-minted-sep28.key`). The primary is the **Aug 29 original**, which is what restored duplicate detection for the 601 — **all of which were deleted later the same day** as test data, so the specific exposure is closed and the rule below is what carries forward.
  - **Key churn is how duplicate profiles got created, and it WILL recur if the key changes again.** `(tenantId, panHash)` is UNIQUE, but the same PAN hashed under a different key yields a different hash, so the index never fires and a second profile is created silently. Eight PANs were each holding two profiles by the time every token could be read under one key. **`InvestorProfile` is empty as of 2026-09-28 but does not stay empty** — `getOrCreateClientProfile()` mints one per (userId, PAN) on every partner print, so the table repopulates from the next print onwards and all of this applies to the new rows. `scripts/restore-pan-tokens.js` (dry-run by default) reports stale hashes and collisions; it has nothing to act on today.
  - **Minting is now OPT-IN.** A missing key file makes the app **REFUSE TO START** unless `PII_VAULT_ALLOW_MINT=true`. Silent minting is what turned a deleted file into unrecoverable data — the process looked healthy while re-keying the vault under everyone. A missing key is either a first install, which an operator can declare once, or an emergency that should stop the process. Both branches are tested: missing + not allowed → refuses with the reason; key present → starts and mints nothing.
  - **The legacy `cwd/.pii-vault.key` path is still READ and still tried on DECRYPT**, so an untouched deployment keeps working and its key can be migrated; it logs a warning naming both paths. `apps/api/.pii-vault.key` (dated Jul 28) is a **stale artefact from a run with a different cwd — it decrypts nothing and is NOT a backup.**
  - **`panHash` is derived from the master key** (`createHmac('sha256', masters[0])`), so a re-key silently breaks duplicate detection: the same PAN fingerprints differently and never matches a stored profile. The **self-PAN rule — one public application per PAN per IPO — stops being enforced against every pre-existing profile, with no error anywhere.** That is the most dangerous consequence of losing this key, well beyond the credentials: a lost credential announces itself, this does not. It is why the key now has an archive and why minting is opt-in.
  - **Back it up OFF this machine.** A dated copy sits beside it (`pii-vault.key.backup-YYYYMMDD-HHMMSS`), which survives a bad command but not a lost disk.
- **`dist` IS NOT A DISPOSABLE BUILD DIRECTORY — it holds LIVE OPERATOR DATA.** `UPLOAD_DIR` defaults to `join(process.cwd(), 'uploads')` (`upload.module.ts`) and under iisnode `process.cwd()` is the entry script's folder, so every DRHP, ASBA template, logo, registrar file and allotment archive lives in **`apps/api/dist/uploads`** — 107 entries as of 2026-09-28, plus `allotment-archive`, `ipo-import` and `catalog-update`. **Never `rm -rf dist`.** Compile straight over it with `tsc --outDir dist`; tsc overwrites what it emits and leaves everything else alone. Attempted on 2026-09-28 and only the IIS worker's file ownership stopped it — every `uploads/` and `iisnode/` path returned *Permission denied* while the compiled JS, which the operator DOES own, was deleted. Recovery was one `tsc` away, but with looser permissions that command destroys the upload store. It is also the real reason the turbo-build warning above matters: nest's clean step targets the same directory.
- Seed is CLEAN-SLATE — never run against prod. Use `npm run ensure-roles` for additive role changes.
- **ALWAYS boot-test before handing the build back**: **`SUBSCRIPTION_POLL_DISABLED=true ALERTS_DISABLED=true PORT=3999 node dist/main.js`** and look for "Nest application successfully started". `tsc` passing proves NOTHING about dependency injection
  - **Set those two env flags, and that is not tidiness** (learned 2026-10-07). Without them the boot test starts a SECOND subscription poller against the production database — benign only while the pool is stopped, and the `dist-check` pattern boot-tests while the pool is UP, which during market hours means two pollers doing `deleteMany` + `createMany` on the same rows.
  - **It also logs `[SubscriptionPoll] Unsupported state or unable to authenticate data` every 10 s, and that is a BOOT-TEST ARTEFACT, not a fault.** It is Node's GCM auth-tag failure: the process's cwd is `apps/api`, so the legacy vault path resolves to `apps/api/.pii-vault.key` — **key #2, the one that decrypts nothing** — and the exchange rail credential will not open. **The live poller is unaffected**; the way to prove that is a recent `subscriptionAsOf`, not the boot log (RKFAL was polled three minutes before the test that produced this warning). So the boot test **cannot exercise the rail-credential path at all** — it proves DI and routing, which is what it is for.
  - **Grep the boot output for the success line specifically, not `head -5`.** Redis's *"highly recommended to use a minimum Redis version of 6.2.0"* notices print between the last route and the success line and pushed it out of view once, which read as a failed boot. — a controller injecting a service whose module wasn't imported fails at BOOT and takes down **every** endpoint with a 500, not just the new route. That happened (`TemplateTestController` → `WhatsappService`, `WhatsappModule` not imported; it is not `@Global`).
- **`web.config` has `loggingEnabled="false"` — there are no iisnode log files.** To see why the API is failing, run the compiled app directly; the Nest error prints in one shot.
- To prove a fix **while the pool is still up**, compile to a scratch dir INSIDE the repo (`--outDir dist-check`, so `node_modules` still resolves), boot-test that, then delete it. `dist` is locked while iisnode runs.

## Conventions
- **Design = "calm & data-clear"** (Apple discipline + functional financial color). Neutral base, hairline borders, indigo on CTAs; **semantic green/red only for financial signals**. Listed chip = light purple; Print Forms CTA = light red `#fdebea`/`#b3372e`. **Never copy competitor UI** (IPOJI/IPOGuru studied for features, not looks).
- Reusable admin UI lives in `apps/web/components/ui` — incl. **SearchSelect** (type-to-filter combobox; list renders via portal because admin `.card` is `overflow:hidden`; also used on the consumer profile form for the UPI handle), **Toast** (top-right toasts), **Tooltip** (below), `.filter-row` (aligns filter fields + buttons; `.field` carries an 18px bottom margin).
- **`Tooltip`** (`components/ui/Tooltip.tsx`, 2026-09-23) — hover / focus / tap popover, **portalled to `body`** because `.ipocard` is `overflow:hidden` (its rounded corners clip the radial wash and the left rail), same reason SearchSelect portals out of the admin `.card`. Three things it got wrong first and now encodes:
  - **`render` is a FUNCTION, not a node.** A list page mounts sixteen of these; the contents (a subscription table each) must only be built while one is open.
  - **A scroll REPOSITIONS it; it does not close it.** Closing looks like the cheap option and is wrong — `HTMLElement.focus()` scrolls its target into view, so tabbing to an off-screen trigger opened the tooltip and the scroll that very focus caused dismissed it in the same tick. It closes only when the trigger leaves the viewport. Scroll/resize are coalesced to one measure per `requestAnimationFrame`.
  - **`z-index: 190`** — above the sticky header (50) and every dropdown (60–80), UNDER the modal overlay (200). A tooltip must never float over a dialog it cannot belong to.
  - Testing note: `el.focus()` is a **no-op when the window itself isn't focused**, which the Browser pane often isn't — a tooltip that "doesn't open" there may open fine for a user. Drive it with `.click()` instead.
- **Web and mobile keep the profile form in step by hand** (different frameworks, no shared component): split UPI input (name grows / handle fixed + filterable) and the one-line NSDL-CDSL explainer exist twice — `apps/web/components/Account.tsx` and `apps/mobile/app/profiles/new.tsx`. Change one, change the other. Widths differ on purpose (handle 158px web / 124px mobile — the phone row has less room).
- **One type contract** — shared types, the bid engine, the glossary, `format.ts` (`titleCase()`, `shortName()`, the `LABEL` vocabulary, `demandWord`), `stage.ts` AND the issue engine (`computeIssue.ts` + `issueRules.ts`) live in `packages/shared-types`. Web and mobile IMPORT these; never re-implement locally. Derived figures used by more than one surface belong in ONE helper too — `categoryLanes()` in `HeroBanner.tsx` feeds both IPO-slide treatments, `issueInputsFor()` feeds every issue derivation.
- **Nest sends an EMPTY body for a `null` handler result** — not the string `"null"` — so `res.json()` throws "Unexpected end of JSON input". Every web API client (`consumer-api.ts`, `tenants-admin.ts`) reads the body as text and treats an empty 200 as `null`. This broke `/partner/apply` for every first-time visitor.
- **`runUnscoped` is not enough on its own for cross-tenant reads on a pooled connection.** `PrismaService`'s tenant extension wraps scoped queries in `$transaction([set_config('app.current_tenant_id', <tid>, true), query])` — `is_local=true` means the GUC resets at transaction end, which works in isolation. But under load the pooled connection can be borrowed while the GUC still carries a value from a prior request, and `runUnscoped(() => findFirst(...))` just calls the query directly without touching the GUC — so RLS on `Application` / `InvestorProfile` silently filters the row out and the handler returns `null`. This 404'd the Print report's View modal for real rows that existed in the DB. Fix pattern: wrap the cross-tenant read in an explicit `$transaction([$executeRaw`SELECT set_config('app.current_tenant_id', ${scope ?? ''}, true)`, findFirst])` — deterministically resets (or narrows to `scope`) before the read, whatever state the connection was in. See `partner.service.ts printDetail` for the reference.
- **Cloudflare/WAF intercepts UUID-in-path patterns under `/prints/`.** `GET /admin/partner-api/prints/<uuid>` returned 404 "Cannot GET" at the browser (Nest default for unmatched routes) even though `curl http://127.0.0.1` from origin returned 401 — the intercept was returning the 404 upstream of iisnode. Moving the ID to a query parameter on a distinct literal path (`GET /print-detail?id=<uuid>`) sidesteps the intercept entirely. Sibling routes `/calls` and `/prints` (list) were unaffected — only the `/prints/<uuid>` shape triggered it.
- **CSS: check for a name collision before adding a class.** `globals.css` is one big global sheet and it has bitten FOUR times: `.sh` inherited a section utility's 76px padding and blew the banner 302→495px; `.nav-link` was defined for BOTH the front-site header and the admin sidebar, and the admin copy (later in the file) dragged `display:flex; gap:11px; width:100%` onto the site nav — the hole between "IPOs" and its count badge (admin rules now scoped to `.admin-side`); a candidate slide named `.steps` hit the apply-flow stepper's `margin: 10px 0 28px`, and since a stretched flex item's height is the container MINUS its margins, that slide rendered 38px short; `.gl-page` lost to `.trust-page`'s later `max-width`. Grep first, prefix banner/page classes (`hb-`, `hbn-`, `hbs-`, `hbp-`, `brd-`, `sd-`). The build catches none of it; **measure the live DOM**.
- **A shared table rule reaches rows you never pictured.** `.fin-tab th:first-child { text-align: left }` exists for the Date column; the day-wise table's SECOND header row *starts* at `bHNI`, so bHNI was that row's `:first-child` and sat a whole column-width left of its own numbers, while `sHNI` (the second cell) looked fine — one header of a pair wrong is the tell. Two lessons: think about every `<tr>` a `:first-child` rule can land on, and **count specificity before assuming an override lands** — `.day-wise-sub thead tr + tr th` (0,1,3) LOSES to `.fin-tab th:first-child` (0,2,1); it took `.fin-tab.day-wise-sub thead tr + tr th` to win. Verify by resolving the computed value in the live DOM, not by reading the rule you just wrote.
- **`--pos-ink` (#0c6b41) is for a LABEL on `--pos-soft`; `--pos` is for fills.** Added 2026-09-28 when the IPO-catalog *Complete* badge went from gold to pastel green (gold collided with Allotment Out in the status colour code, and a hard outline made a 10px chip read as a button). The obvious `color: var(--pos)` on `var(--pos-soft)` measures **3.50:1 — it FAILS WCAG AA for text**, and the gold it replaced was 5.75:1, so the pretty version was the less legible one. `--pos-ink` is 5.80:1 and was already the hex `.banner.ok` paired with that fill, so this is a token promotion, not a ninth palette. **Measure the pair before shipping a tint — a nicer chip that is harder to read is not an improvement.** Verified by resolving the `var()` chain in the SHIPPED bundle, per the rule below.
- **Prefer explicit values over "looks about right"** when two controls must match: the status track and the board meter are both pinned to a stated 40px (32px button + 3px padding + 1px border), not to padding that drifts the moment a font size changes.

## Subscription poller — cadence + tuning
- **Live-tunable via `admin → Integrations → 'Live subscription poller — cadence & window'`**. Provider key `subscription` with fields: `normalSec` (default 60), `fastSec` (default 5), `fastWindowMin` (default 90), `fromMin` (default 600 = 10:00), `toMin` (default 1080 = 18:00). Poller reads `providers.effective('subscription')` on each tick with the 60s config cache TTL, so overrides take effect within a minute — **no pool restart** needed for cadence tweaks. Bad values (non-numeric, ≤0) fall back to defaults per-field so a typo can't stall the loop.
- **Window: 10:00–18:00 IST**. `OPEN_TO_MIN` is `18 * 60` — 1-hour grace past the 17:00 SEBI bidding cutoff so NSE catwise and BSE demand-schedule can serve consolidated / finalized numbers for another 30-60 min on closing day. Was 17:00 sharp until 2026-09-21 when NSE's final subscription never got written.

## ASBA print — flatten guarantee for WhatsApp forwarding

- **W-SUB — the form warns when an issue that has NOT CLOSED YET has no reservation split** (operator ask, 2026-10-06, after ten SME issues closed with nothing). It is the most expensive omission on the screen and **the only one whose cost is irreversible**: with no percentages the poller has no denominator, so it fetches the exchange's demand and throws it away on every tick, and a bidding day that passes cannot be recovered afterwards — the usual rescue, `nseShares ÷ timesSubscribed`, needs a row that was written. See the poller section for the mechanism.
  - **A WARNING, not a blocker, deliberately**: an issue is often entered before its RHP is out and the percentages genuinely are not known. Blocking the save would mean the record is not entered at all.
  - **It needs a CLOSE DATE to fire**, which keeps it quiet on a half-typed new record and on the ~1,200 closed historical rows where the data is already gone and the warning would be pure noise.
  - It is a FORM rule, not an engine one — the third alongside **B04** and **E-RESV** — because "has this issue closed yet?" is a question about today, which `computeIssue()` is never asked.
- **W04 · W05 — two rules added 2026-09-30, both WARNINGS, both calibrated against the catalogue BEFORE they were written.**
  - **W04, the minimum application VALUE.** A mainboard bid lot belongs between **₹10,000 and ₹15,000** at the primary price, which makes it the cheapest guard there is against a mis-keyed lot size — the class of error that let SPECTRAA publish ₹1 Cr. **470 of the 471 mainboard records already sit inside the band**, and the ONE exception is an **FPO** (Adani Enterprises, lot 4 × ₹1,638 = ₹6,552), which is priced against a listed market price and not under the IPO minimum-bid rule. So the check is scoped to `instrument: 'ipo'` — a new `IssueInputs` field — and **without that gate its only firing would have been a false positive**. It is **silent on SME**, where the individual bid is two lots and no rupee band expresses it; `lotValueRange` is simply absent from those packs, the same way B11/B12 go quiet outside a known holiday year. Fires on **0 of 986** derivable records.
  - **W05, the shareholder reservation cap** — ICDR's 10% of the issue size. **No record in the catalogue carries a shareholder carve-out**, so this fires on nothing and is a guard for the historical import, not a repair. A warning rather than a blocker on purpose: the cap is well attested, its BASIS (issue size vs post-issue capital) is worth the operator confirming, and the message names the basis so that judgement can be made from the screen. **The EMPLOYEE cap deliberately has no rule** — ICDR measures it against POST-ISSUE CAPITAL, which the engine is never given, and a check against the wrong denominator is worse than none.
  - **Its own test caught the round-vs-floor trap, again.** W05 first divided by `primary.totalOfferShares` — the ALLOCATION total, floored to lot — so a reservation of *exactly* the cap read as **10.00001%** and fired. `ScenarioResult` now carries **`totalOfferOffered` / `netOfferOffered`** beside the allocation pair, as `netQibOffered` already did. Even then the tolerance is **one LOT, not a float epsilon**, because `totalOfferOffered` still inherits a floor when the offer is described by LEGS alone with no stated count and no ₹ total. **Before comparing any two figures here, check which basis each one is on.**
- **B02 enforces the NII split as a RATIO, not as `10` and `5`.** `RulePack.niiSplit` used to be `{big:10, small:5}` and was never read by anything; it is now `{big:2, small:1}` and drives the check. Absolute per-row bounds would be wrong: ICDR sets a *floor* on NII under 6(1) and a *ceiling* under 6(2), not an exact figure, so a 6(1) issuer may legally offer 24/12 — which a hard `max: 10` would reject. `bounds` is now `Record<string, CategoryBound>` keyed by category, plus the pseudo-key **`nii`** for the combined quota (a 20% NII split correctly 2:1 looks fine row by row and is caught only in aggregate). **Big < Small blocks** (the transposition, a data-entry defect that published wrong figures on three records); an off-ratio split that is not transposed is **W01, a warning** — an unusual split is the issuer's business. B01 *has* to: Step 3 absorbs the floor-to-lot residual into one category, so a table summing to 99.9% still satisfies `Σ shares == net_offer_shares` and every post-condition passes — the shortfall is silently handed to the residual holder. Checked only in the admin form (as it was), the Excel importer and the API derive a clean-looking wrong answer. **B09/B10 don't stack**: a fixed-price pack caps the anchor at 0, so reporting both would tell the operator to *reduce* a percentage they need to *remove*.
- **Anchor % of QIB is now an input** (`extra.anchorPct`, Offer & Reservation tab) with anchor shares / net QIB derived beside it. The net-QIB readout is `anchor.netQibOffered` (published basis) while the MF sub-splits stay on `netQibShares` (allocation basis) — see the two-figures rule under Subscription surface. Before this the rule pack's `anchorMaxPctOfQib: 60` existed with nothing to compare against — B09 was unreachable from every surface.
- **Derived values are no longer persisted.** `shareResv[k]` stores `{on, pct}` only — `count` / `req1x` / `remark` are stripped on save AND on load, so a legacy record sheds them the first time it is opened. `extra.retailCutOff` is no longer written. `admin/catalog/view` was the last reader of all four and now derives from the same engine; it also stopped reading `extra.sharesSize`, which the form had **stopped writing** when that grid was dropped (a dangling read that rendered stale rows on old records and nothing on new ones).
- **Working days come from a REAL NSE calendar** — `packages/shared-types/src/holidays.ts`, the CM (equity) segment of `nseindia.com/api/holiday-master?type=trading`, each date carrying the reason it is closed. **Regenerate every January**: NSE only ever serves the current year, and `HOLIDAY_YEARS` is what **B11/B12 check before they dare to BLOCK** — outside those years they fall back to counting weekends and say so in the message, because a blocking rule that is guessing stops an operator entering a valid issue. Why it was worth doing: close Mon 30 Mar 2026 → list Mon 6 Apr is **seven calendar days and exactly T+3**, because Mahavir Jayanti (31st) and Good Friday (3rd) both fall in between. Counting weekdays called that T+5 and flagged a correct issue. (NSE's homepage 403s a server-side fetch but the API itself answers 200.)
- **What the entry screen can and cannot take** (audited 2026-09-30 when the operator asked whether the team can now add any type of IPO). **Can**: mainboard and SME · book-built and fixed-price · ICDR 6(1) and 6(2) · Fresh and OFS legs in ₹ OR shares · employee / shareholder / policyholder / market-maker carve-outs · anchor as an estimate or an actual allotment · **FPO** (4 in the catalogue; W04 exempts them from the minimum-bid band). **Cannot**, and both are worth knowing before someone tries:
  - **REIT and InvIT are in the `Instrument` enum but have NO rule pack.** `packFor` falls back to `mainboard/book_built/icdr_6_1`, whose bounds (QIB ≤50 · NII ≥15 · Retail ≥35) are not how a REIT allocates — so a REIT would validate against IPO rules and look fine. Latent only because the **IPO Category master holds just two rows** (Mainboard, SME), so the picker cannot reach them. **Add the pack before adding the category, not after.**
  - **Buyback and standalone OFS are not modelled at all** — the Excel importer counts and parks those sheets. Still the pending decision below.
- **Start Bid / Start Print / Is Active stay INDEPENDENT toggles** (operator decision, 2026-08-29). The status machine is not coming for them; Review & Publish shows every failing check beside the toggles but never overrides the operator. Do not re-propose gating them.
- **Deliberately NOT done, and why**: the status machine (replacing Start Bid / Start Printing / Is Active — **18/16 consumer files incl. the partner Print API**) and the entity tables (per-category bid windows — **dates are read in 15 API files** — typed intermediaries, structured financials/objects). Both are far cheaper BEFORE the real catalog is entered.
- **Regulatory rupee thresholds live ONLY in `issueRules.ts`**, as three named exports: **`RETAIL_MAX_AMOUNT`** (₹2 L — retail ceiling, cut-off eligibility, shareholder cap) · **`SNII_MAX_AMOUNT`** (₹10 L — above it is B-HNI) · **`UPI_MANDATE_MAX`** (₹5 L — UPI cap, a PAYMENT rule) · **`ASBA_SYNDICATE_ABOVE`** (₹5 L — the resident-vs-syndicate ASBA form split, a FORM-TYPE rule). An audit on 2026-08-27 found them retyped at **ten** sites; all ten now import. **`apps/api` gained a `@investoyard/shared-types` dependency** to do it — it had none before; both packages are CommonJS/ES2021 and the root workspace symlink resolves under iisnode (proven by boot test, and `@investoyard/rail-adapters` already worked the same way).
- **Grep with underscores AND without.** `200_000` evades a `200000` search — that is how two of the sites stayed hidden through the first pass, and how the sweep later turned up four MORE than the audit had catalogued (`ASBA_RETAIL_LIMIT` in the API, plus `upiCap` fallbacks in `web/lib/tenants.ts`, `mobile/lib/api.ts` and `mobile/app/apply/[symbol].tsx`).
- **`DEFAULT_BID_RULES` must stay numerically identical** across any change here — it drives live apply validation. Assert it (`{retailCap:200000, bhniAbove:1000000, syndicateAbove:500000, upiCap:500000}`), don't eyeball it.
- **Still NOT what the brief asks for**: it wants **seed config** — a versioned table with `effective_from`, admin-editable. `issueRules.ts` is *source*, so a SEBI amendment remains a deploy, not a config edit. That is Phase 1 and is not built. The percentage bounds (`75`/`15`/`10`/`50`/`35`) also still live in the `RULE_PACKS` literal.
- **Three of the 7 records with a reservation table now fail validation** (2026-08-27, all invisible until the rules existed). **ARDEE** raises both of its faults by itself now — retail 15% against the ICDR 6(1) floor of 35%, *and* Big 15 / Small 20 transposed — which is exactly why `fix-hni-swap.js` refused to touch it. It still needs the RHP, but the screen states the diagnosis. MVELECTRO and HORIZON, the two that script did repair, come back clean.
- **Two live records fail validation, and as of 2026-09-26 they fail on DIFFERENT rules** — look for the right one. **AUGMONT** raises **E-RESV**, not B01: its 0.691% employee row is now excluded from the split, so Σ reads a clean 100.000% and B01 passes. The fault is unchanged — a 0.691% **employee quota sits in the reservation table when it belongs in the carve-out** (spec §2.5: carve-outs come off the top *before* the percentage split) — but the diagnosis moved from "the percentages overshoot" to "this quota is read nowhere", which is the more honest statement. AUGMONT is one of the 3 fully-derivable records, so it published figures with that overshoot absorbed into QIB for as long as the row was counted. **PRIORITY** still fails **B01** at Σ = 50% — only the QIB row was ever entered, so QIB absorbs the whole net offer and every derived number on it is wrong. Both need the operator, not a script.
- `floor_to_lot` everywhere with residual absorption; `ceil` for applications-to-reach-1× and `floor` for allotment capacity — two different numbers the old code conflated. `Math.round` under-reported the first.
- **HNI Big/Small**: `hni` = Big, `hni2` = Small; SEBI gives Big the larger two-thirds of NII. Three records were transposed — MVELECTRO + HORIZON repaired by `scripts/fix-hni-swap.js` (**dry-run by default**, only touches a known-safe signature); ARDEE flagged, not rewritten (its split also breaks the retail floor — needs the RHP). The form now warns when Small > Big.
- **Two figures used to be invented and printed as fact**: Fresh/OFS was `issueSize × 0.85 / 0.15`, and the API wrote `['NSE','BSE']` for every mainboard issue regardless. Both are real inputs now; the exchange guess survives only as a fallback for the Excel importer.
- `Ipo.status` is effectively dead (all rows `upcoming`; status derived at read time by `effectiveStatus()` / `stageOf()`), and `Ipo.reservations` (quota NAME list) is NOT `extra.shareResv` (the percentage table). `Ipo.issueSize` is RUPEES, `issueSizeCr` is Cr — mixing them is a 10⁷ error.

## Messaging: delivery log + test sends
- **Every send is logged** — SMS, email, WhatsApp — from the **LEAF adapters** (`SmsService.send` · `EmailService.send` · `WhatsappService.graphSend`), never from their callers. OTP calls `SmsService` DIRECTLY and bypasses `MessagingService`, so logging at the caller would miss the messages most worth tracing. `MessageLogService.record()` never throws.
- Recipients are stored **masked** (`98XXXX1234`) with `recipientLast4` as the search key — a support tool, not a contact list. Changing that is one line in `maskRecipient()` but should be a deliberate DPDP call.
- Admin → System Settings → **Message Log**; **Test** button per template shows the rendered body beside the provider's reply and the DLT template id (a DLT rejection is nearly always a text mismatch).
- Nothing is backfilled — the log starts at the deploy.
